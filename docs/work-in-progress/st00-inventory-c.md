### Anomalies / build blockers

- **ArtCraft depends on the absent `artcraft-services` repository** — backend APIs, the alternate webapp referenced by `artcraft-native/README.md`, and enum sources of truth are external; generation features cannot be exercised locally. Also `frontend` has no lockfile-committed `package.json` version alignment guarantee (`"version": "0.0.0"`).
- **ArtCraft has no never-crash discipline**: `lib.rs` uses `println!` (violating its own crates/AGENTS rule contextually), `.expect()` and an explicit `panic!` at startup (`lib.rs:102,133,203,294`); the sibling craft-app invariants (clippy deny lists, `unsafe_code=forbid`) are absent; the three plugin-host-adjacent risks don't apply but `tauri = { features = ["unstable","devtools"] }` blocks App Store distribution (comment in Cargo.toml).
- **Dead command surface in ArtCraft**: `deprecated/{image_edit,image_inpaint,text_to_image}` + `app_state/reset_artcraft_command` are compiled `#[tauri::command]`s absent from the handler; the TS side still ships invoke wrappers for them.
- **cadcraft `acadrust` (MPL-2.0)** is the one weak-copyleft dep across all four apps — isolated behind `crates/dwg`, recorded in `NOTICE:10-16` (must survive ST-01 forking).
- **soundcraft MIDI is file-only**: SMF + ops exist, but there is no `midir`/device endpoint code; `setup.midi_*` commands store names rather than open devices — record as a fidelity gap, not a stub-fraud.
- **cadcraft `plot` ≠ printing**: it renders a PDF via `io::pdf::plot`; no OS spooler integration (unlike pdfcraft's real CUPS/printui path).
- **pdfcraft vendored crates** (`vendor/` hayro×4, lopdf, winit, egui-wgpu) are workspace `[patch]`es — forking must preserve `vendor/` verbatim.
- All three craft apps declare `edition 2024` / `rust-version 1.90` — a very new toolchain requirement for ST-00(a) environment evidence; artcraft has **no MSRV** and edition varies (`artcraft-native` = 2021).

### Confidence gaps

- SoundCraft's exact spec count is ~259 grep hits on the `cmd!` macro pattern; a few multi-line invocations could add a handful — the registry test only asserts `>150`. Count reported as ~259, not exact.
- CADCraft's 287 ids include 2 macro-generated template lines (`run_gc`/`run_dc` CommandSpec::new in `gripcmds`/constraints helpers) — effective distinct ids ≈ 285; family counts above treat them as registered.
- ArtCraft: registered-vs-defined delta — 63 registered handlers + 4 unregistered `#[tauri::command]` files vs 63 total files seen in grep; some registered commands may be defined under macro patterns not matching `#[tauri::command` (e.g. `generate/omni`), so the unregistered set may be slightly larger than 4. Registered list itself is authoritative from `lib.rs:227-291`.
- pdfcraft automation tool count (~124) derived from `t("` literals in `tools.rs`; a couple of names are produced via concatenated const strings — order-of-magnitude safe; `command_run` dispatch in `lib.rs` is the authoritative list.
- No `cargo`/`npm` was run (per constraints), so `Cargo.lock`/`package-lock.json` versions were read as text only; `artcraft` frontend `package-lock.json` was not audited line-by-line.
