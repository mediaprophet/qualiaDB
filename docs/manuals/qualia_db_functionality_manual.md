# Qualia Ecosystem Complete Functionality Manual

**Generated On:** 2026-07-12
**Scope:** Entire Project Workspace — all 18 crates under `crates/` (QualiaDB core engine, client/CLI orchestration, physics/quantum extensions, desktop & studio UI, rendering/runtime/browser-embedding support, cooperative governance, knowledge/interop tooling, the companion-device bridge, and the Wellfare health-vault application).

Qualia is a zero-allocation, mechanically sympathetic semantic database and multi-agent collaboration ecosystem. This manual provides an exhaustive, up-to-date breakdown of the functionality currently available across the *entire project*, derived directly from the source code.

**A note on honesty (house rule, CLAUDE.md §12):** several crates below contain genuine, working functionality sitting alongside explicit stubs, mocks, or dead scaffolding. Where that is the case, this manual says so plainly and names the exact function or file — describing a stub as shipped functionality is treated as a documentation failure here, not a shortcut.

## 1. Core Database Engine (`qualia-core-db`)

The foundational semantic graph engine — by far the largest crate in the workspace (~460 `.rs` files across ~35 subdirectories) — bridges the Semantic Web with hardware-aligned execution paths, enforcing strict constraints to ensure bounded memory and deterministic performance.

*   **Zero-Heap & Super-Quin:** Enforces strict zero-allocation in hot paths. Semantic data is packed into a 48-byte `NQuin` struct, persisted as 40,960-byte `QualiaSuperBlock`s (`lib.rs`), and `lib.rs` publishes `CAPABILITY_DESCRIPTORS`, a self-reported maturity table (stable / partial / experimental / fail-closed) for every capability family.
*   **Storage & Persistence:** Cross-platform storage backends (ZNS NVMe zone-append, APFS clonefile, WinNVMe, Mmap) behind `open_storage()` (`storage.rs`, `storage_driver.rs`, `zns_storage.rs`, `csd_storage.rs`), backed by a tamper-evident, ed25519-signed Write-Ahead Log (`wal.rs`) that also records Webizen VM conduct violations. `wasm_storage.rs` is the real, wired WASM-target counterpart — pure-Rust SuperBlock packing with real per-quin XOR-parity ECC, plus async OPFS block read/write and storage-quota estimation, live-consumed by `docs/playground/ingest_worker.js` (loaded from the ontology/WordNet browser apps) and `docs/js/qualia-icp-vault.js` (loaded from `docs/phone-console.html`) — distinct from `qualia-mobile-harness`'s unrelated, unwired OPFS worker (§8).
*   **Native LLM Inference Stack — no llama.cpp, no Python, no HTTP server (but see the Ollama *fallback* caveat below):** `gguf_sharder.rs` contains two parallel implementations, only one of which production code actually uses. `GgufTensorIndex` (the real one) does genuine GGUF header/KV/tensor-info parsing — real byte offsets, real tensor names — and is what `gguf_bridge.rs`, `p64_weight.rs`, `inference_agent.rs`, and ~90 other call sites consume directly. `GGufSharder::generate_bidx_pointer_map` — the function CLAUDE.md's own top-level orientation cites for "NQuin pointer map" generation — is a *different*, reachable-in-production function that **fabricates** synthetic linear offsets (`0x1000 + i*0x4000`) and fake tensor names instead of reading the real tensor-info section 350 lines away in the same file; it's called from `model_lifecycle.rs`'s `install_catalog_llm` and `vision_ingest.rs`, writing these synthetic offsets to the WAL as if they were real provenance, and reporting a `pointer_quin_count` to the CLI user that looks meaningful but isn't. The bit-packing mechanism itself (`upper 4 bits = modality flag 0b1001`) is correctly implemented — only the byte-offset payload it packs is fake. `gguf_bridge/` (25 files) maps model weights via `memmap2` straight into the OS page cache and dispatches fused transformer blocks to the GPU; `inference/` (52 files) runs the real two-thread Phase 8 bifurcated autoregressive decode loop (real native GPU decode — LoRA application, speculative/topology-draft decode, neuro-symbolic sieve output — confirmed by full-file read of `inference_agent.rs`) via two genuine wait-free SPSC rings (`rtrb`) separating an LLM-engine thread from a Sentinel thread on the calling side. **However, the Sentinel's anomaly detector is inert**: every `LogitSummary` hardcodes `anomaly: 0x01` ("normal") — a prior heuristic that corrupted the stream was removed and never replaced, so `DenyRollback` never fires from a real governance signal today; the only live rollback trigger is an unrelated draft-emptiness check, and even that doesn't cause recomputation, only a log line. The architecture (`orchestrator` with `ModelLifecycle`/`ThermalGovernor`, `sampler`, `ternary`, `resident_model`, `quant_graph_grounding`) is real and load-bearing — the mid-generation anomaly-rollback *behavior* CLAUDE.md describes is scaffolding without a live detector, not yet a working safeguard.
*   **Inference GPU Dispatch, Decode-Loop & Telemetry — further full-file findings beyond the Native LLM Inference Stack bullet above:** the GPU backend group (`cuda_lane.rs`, `directml_bridge.rs`, `metal_bridge.rs`, `ternary_gpu.rs`, `topk_gpu.rs`, `inference_gpu_profiler.rs`, `compute_universe.rs`, `ggml_quants.rs`) is uniformly real, with no fake-kernel pattern anywhere in it. `cuda_lane.rs` is genuine CUDA via the real `cudarc` crate, compiling and launching real CUDA-C kernels (`Q4K_SOA_GEMV_SRC`, fused SwiGLU, SDPA decode) with device-resident weight caching. `directml_bridge.rs` does genuine DirectML device/operator/dispatch calls, but contains two explicitly-labeled honest stubs: an IOCP FFI firewall ("Stub implementation... returns error until DirectX version conflicts are resolved") and a `DirectStorageManager` whose `async_read_to_gpu` always returns `NotImplemented`. `metal_bridge.rs` is genuine Accelerate-framework FFI (`cblas_sgemm`), exercised by an on-silicon smoke test. `ternary_gpu.rs`/`topk_gpu.rs` dispatch real `wgpu` compute pipelines, each parity-tested against a byte-exact CPU oracle that skips cleanly (not fakes a pass) with no adapter present. `compute_universe.rs` is not a competing type versus `gpu_context.rs`'s `ComputeUniverse` — the enum is defined exactly once in `gpu_context.rs`; the `inference/` file only adds extension methods and hosts the Phase-8 SPSC context/topology-draft rings that consume it. `ggml_quants.rs`'s Q6_K dequantization is tested end-to-end against a real GGUF fixture file, diffed against hand-copied llama.cpp reference floats.

*   **SPARQL & Query Engine — including real SPARQL-Star, plus a tier of unwired sibling libraries:** `sparql_library/` (~21 files + `parsers/`/`rdf_formats/`/`serialisers/` subdirs, ~14,800 lines) has one real, live execution path — `sparql_parser::parse_sparql` → `sparql_planner::QueryPlanner` → `sparql_executor::QueryExecutor` — shared by HTTP `/query`, MCP `query_sparql`, and WS `/qualia-bridge` (`services/daemon_query.rs`). This covers SELECT/ASK/CONSTRUCT/DESCRIBE, property paths, aggregates, and filters, and genuinely includes **SPARQL-Star**: `<< s p o >> outerP outerO` quoted-triple patterns parse into a real `StarTripleScan` operator and execute end-to-end against virtual-ID-tagged `NQuin`s (minted by real RDF-Star parsers for Turtle/N-Triples/N-Quads/TriG/N3), not just declared. Two Star gaps found by the audit were **fixed 2026-07-12**: the `TRIPLE()`/`EmbeddedTriple` FILTER evaluators hashed arguments as `s^p^o` (order-insensitive, no tag bit — never matched a stored quoted triple) and now mint the canonical `generate_embedded_triple_id`; and Turtle-Star ingest discarded the annotation's outer predicate/object, so it now captures them and emits the linking statement (parity with the N-Quads-Star parser) rather than dropping the virtual id. **Caveat — see the parser-scope note at the end of this bullet:** the `TRIPLE()` FILTER fix is correct at the evaluator (unit-tested), but a *live query* still can't reach any FILTER function because the SPARQL parser does not parse FILTER at all. `sparql_shacl.rs` (documented under SHACL, §1 above) is the real `sh:sparql` constraint evaluator sharing this same executor. Separately, the directory also holds a tier of **implemented-but-unwired libraries** — real code, real unit tests, but never instantiated outside their own file's tests, because `sparql_executor.rs`/`daemon_query.rs` never call them: SPARQL UPDATE (`sparql_update.rs` — real INSERT/DELETE DATA and DELETE/INSERT WHERE logic, but capped at a fixed 64-triple array per statement, and `LOAD`/`CREATE` are explicit stubs), SERVICE-clause federation (`sparql_federated.rs` — local `qualia:`/`local:` endpoints genuinely execute, remote HTTP endpoints honestly return a placeholder with no forged results, by the module's own documented design), WebSocket query/subscribe sessions (`sparql_websocket.rs` — real query/format/chunk logic and subscription bookkeeping, but nothing ever calls `notify_subscribers` on a mutation and no transport/listener exists to receive connections), and a magic-predicate extension registry (`sparql_extensions.rs`) for GeoSPARQL/SPARQL-MM/C2PA/DID functions that `sparql_executor.rs` never looks up at all — and even if wired, several of its GeoSPARQL functions are explicit "Simplified" placeholders (the three C2PA duplicate-hash-key collisions that silently dropped `created_at`/`created_by`/`verify_signature` were **fixed 2026-07-12** — all seven now register). `sparql_mm.rs` (SPARQL-MM temporal/spatial media fragments) is real data-structure/windowing code but functionally decorative for its stated purpose — its MA-Ontology/C2PA predicate-hash constants are hand-written hex literals, not real `q_hash()` outputs, so they can never match real ingested data (two of them are even the literal same value). `sparql_did.rs` reverifies and extends CLAUDE.md §8's claim: `sign_with_did` still fails closed with no forged signature as documented, and the same intentional fail-closed pattern extends to `check_permission`/`authenticate_did` too — real Ed25519 verification exists behind the `interop-crypto` feature. `serialisers/` (two conformance gaps **fixed 2026-07-12**): `sparql_results.rs` previously emitted every binding as `"type": "uri"`; it now detects inline-typed literals (xsd:integer/decimal/boolean/float) via the new shared `resolver::classify_inline_literal` and emits proper `literal`+datatype JSON/XML (blank nodes remain indistinguishable — they are hashed into the IRI space at ingest, an upstream limitation). `rdf_serializers.rs`'s Turtle/TriG/N3/JSON-LD paths emitted opaque `urn:hash:...` placeholders; they now resolve IRIs through the same resolver the N-Triples/N-Quads paths use (`urn:hash` only as a last-resort fallback). Both changes carry regression tests. `query/` hosts the `mini_parser`/`resolver`/`ontology_loader` ingest pipeline backing the `/query` endpoint, plus the shared 60-bit lexicon primitives (`q_hash`/`generate_60bit_token`/`generate_embedded_triple_id`) that both the SPARQL engine and the RDF-Star virtual-ID scheme depend on — the directory is larger than the three named files suggest, but wasn't independently deep-audited beyond confirming lexicon is the real dependency root. **Root-cause note on the whole unwired tier (verified 2026-07-12):** the deeper reason UPDATE, SERVICE federation, and the FILTER/extension-function machinery are unreachable is not merely that the executor doesn't call them — it is that `sparql_parser.rs` (665 lines) is a minimal string-slicer that parses only SELECT/ASK/CONSTRUCT/DESCRIBE + PREFIX + basic WHERE triple patterns. It parses **no FILTER, SERVICE, OPTIONAL, UNION, MINUS, BIND, or update syntax**, and never constructs an `Expression::Function` node (those exist only in unit tests). So the real executor *does* evaluate filter expressions and dispatch a `Service` operator when handed one — but the parser never produces them. Making the extension registry, SERVICE clause, or a live `TRIPLE()` FILTER usable therefore requires a real SPARQL expression/clause grammar in the parser (a substantial feature), not a dispatch-wiring change. The Wave-1 correctness fixes above are at the evaluator/serializer/ingest layers, which are exercised by the tests and the parts of the pipeline the parser *does* reach.

## 2. Client API, CLI & Local Orchestration (`qualia-client-core`, `qualia-cli`)

The client core acts as the intermediary between the database engine and user-facing applications; `qualia-cli` is the command-line front end for the whole engine.

*   **Client Core (`qualia-client-core`, v0.0.23, ~52k lines across ~90 top-level modules plus `wellfair/`, `chora/`, `wallet/`, `engine/`):** the native application/orchestration layer between the graph/inference engine and the Webizen UI shells.
    *   **Chat & Real Inference — deeper than the file list implies:** `chat_session.rs`, `chat_retrieval.rs`, `chat_ontology.rs`, `chat_files.rs` cover WAL-backed session persistence, scoped `.q42` retrieval, WordNet-grounded discourse, and attachment ingest (including real image binding via `vision_ingest.rs` — SHA-256 hash + `q_hash` lexicon id + provenance/vision `NQuin`s appended to a dedicated WAL, gated on an actually-active multimodal model; distinct from the separate `qualia-vision` crate in §7, which does detection, not WAL binding). `chat_graph.rs` is specifically a span-anchored reply/fragment DAG — `ChatFragment` (a selected text span, author, anchor offsets) plus `ChatGraphEdge` parent/child links carrying a branch-type/label/emoji taxonomy and a WordNet-grounding hash — not a citation/provenance-of-external-sources DAG. `chat_relay.rs` is real but is HTTP publish/pull polling (signed envelopes, Lamport cursors, `/chat/publish`+`/chat/pull` against per-contact relay endpoints) — the actual mesh transport is separate: `mesh_channel.rs` (312 lines) is a pure, dependency-free reliable-delivery protocol (sequence numbers, ACKs, timed retransmit, a 4096-entry dedup window) layered over the best-effort WireGuard mesh, and `chat_mesh_service.rs` (305 lines) is the live dedicated thread that actually runs it — publishing/ACKing/retransmitting chat envelopes over the mesh and either applying or forwarding newly-delivered ones;     *   **Sanctuary Vault — anti-coercion protection (`wellfair/sanctuary_vault.rs`, 1,609 lines):** a real, adversarially-tested "rubber-hose resistance" system defending a person being physically or relationally forced to unlock their own data. A dual-lane encrypted vault: the real PIN opens the real lane; a separate duress PIN opens an independent, differently-keyed decoy lane that looks like the whole vault to a coercer. There is deliberately **no destructive "nuke PIN"** (a coercer discovering self-destruction is itself dangerous) — instead, whatever happens in the decoy lane under duress is sealed via anonymous X25519 ECIES to a key only the real lane can later decrypt, building a blind audit trail the victim can review once safe, via `review_decoy_activity`/`RetentionMode` (auto-archive or manual triage). Real Argon2id KDF, AES-256-GCM per-lane AEAD, equal-KDF-work lane resolution (both lanes always take one full stretch before branching, to avoid a timing tell), a PIN-strength floor, and optional OS-keychain-peppered vaults with recovery codes. `vault_container.rs` is the CBOR-native, constant-slot-count on-disk container. Wired end-to-end: `wellfair/api.rs`'s `setup_sanctuary_vault*`/`review_decoy_activity`/`get_/set_retention_mode` → real `webizen-desktop` Tauri commands → `webizen-studio`'s `sanctuary_panel.rs`/`decoy_retention_panel.rs`, the latter of which deliberately **refuses to render at all in a decoy session** ("a person who was forced to open the cover space must not learn that a record is being kept") and uses deliberately plain, jargon-free copy. `crates/qualia-core-db/tests/sanctuary_audit_adversarial.rs` (528 lines) is genuinely adversarial — every single-byte mutation of the sealed box, wrapped key, and AAD is verified to fail closed, never panic, across hundreds of combinatorial cases. **One correction from a full audit of `webizen-studio`'s `host_client.rs`, found and fixed 2026-07-12** (the shared Tauri-invoke bridge for all ~34 wellfair panels, 145 wrapper functions, 3,763 lines): its non-wasm32/non-Tauri-host fallback pattern is documented elsewhere in this manual as "honest `Err`, never fabricated success" — that held for 143 of 145 wrappers, but `set_decoy_retention_mode`'s non-wasm32 stub was the **one mutation that broke it**, returning `Ok(())` as if a security-relevant duress-audit-retention-policy write succeeded when nothing happened, and its sibling `get_decoy_retention_mode` fabricated a specific `"auto_archive"` value rather than an honest empty/error result. Both now fail closed with the same `"requires the Tauri desktop host"` error every other wrapper uses — the panel already had an honest error branch (it shows "Couldn't load/save this setting"), so no caller broke. This was an isolated oversight, not a design choice, and mattered because the surrounding system is explicitly built to avoid exactly this kind of false-success signal.

## 3. Physics, Quantum & Neural Compute Extensions (`qualia-extensions`, `qualia-q-forge`)

Heavier, non-zero-allocation compute work the core engine deliberately excludes lives in a separate extensions crate, plus a small `no_std` quantum-simulation crate it optionally depends on.

*   **`qualia-extensions`** plugs into the core via an `Extension` trait + `ExtensionManager` registry (`lib.rs`), which also exposes a C-ABI FFI bridge (`extension_manager_new`/`execute_job`/`free`), a standalone TCP daemon (`bin/daemon.rs`, port 8080), and a clap CLI (`bin/cli.rs`).
    *   **PINN Extension:** `pinn_extension.rs` — a real ternary (1.58-bit) MLP forward pass (`ternary_forward`/`pinn_forward`) and a genuine finite-difference PDE residual (`pde_residual`) for heat/Lorenz/Navier-Stokes constraints, falling back to exact analytic references (heat kernel, RK4 Lorenz, Taylor-Green vortex) when a model has no trained weights.
    *   **SNN Extension:** `snn_extension.rs` — real LIF integrate-and-fire dynamics with exponential membrane leak, refractory periods, and STDP plasticity (`step_neurons`), plus a "noisy gradient CRDT" that performs a genuine single-node merge/conflict-resolution.
    *   **QPU Extension:** `qpu_extension.rs` — real circuit validation and a real local statevector simulator via the optional `qualia-q-forge` feature.
    *   **WebGPU Physics Solvers:** `webgpu_extension/` — real CPU-reference numerics validated against analytic solutions: `fluid.rs` (incompressible 2D Navier-Stokes via Chorin's projection method, matched to the exact Taylor-Green decay rate), `electromagnetics.rs` (Maxwell FDTD), `heat.rs`, `wave.rs`, `particles.rs` (N-body), `tensor.rs` (dense GEMM), plus WGSL kernel source in `shaders.rs` for eventual GPU dispatch through the core engine's shared `wgpu` device.
*   **`qualia-q-forge`** is a `#![no_std]`, zero-heap-allocation crate: `qasm/parser.rs` hand-parses a subset of OpenQASM 3 into a fixed-capacity 256-statement AST, and `sim/statevector.rs`'s `StateVectorSimulator` executes gates as category-theory `Morphism`s (via `qualia-core-db::specialized_libs::category_theory`) over a caller-supplied state vector, decoding instructions from bit-packed `NQuin` records.

**Known limitations in `qualia-extensions`:** the QPU extension's remote-provider execution (`execute_ibm_quantum`/`execute_google_quantum`/`execute_aws_braket`) is explicitly mocked — hardcoded bit-string counts and fidelity numbers, not real network calls, despite provider endpoints and a `reqwest` dependency being wired; only the local statevector simulator (via `qualia-q-forge`) is real. PINN's `native_neural_forward` is commented "not yet wired" and falls back to the analytic reference instead of the real `wgpu`/GGUF pipeline; its `simulate_fluid`/`predict_chaos` job operations return empty stub results with hardcoded execution times. SNN's CRDT gradient sync has no actual multi-node network transport despite declaring `requires_network: true`.

**Known limitations in `qualia-q-forge`** (status: experimental): `parser.rs::parse_gate_decl` explicitly skips the gate body ("stub implementation") — user-defined gate semantics are discarded. The parser covers only `OPENQASM`/`include`/`qubit`/`gate`/gate-call statements — no classical registers, measurement, or control flow, and `QasmProgram` is hard-capped at 256 statements. `statevector.rs::execute_circuit` supports exactly 4 gate opcodes (X, Z, H, CX); the `NQuin` opcode/operand encoding is explicitly called out in-comment as an assumed placeholder. `sample()` is not real probabilistic sampling — comments call it "extremely rudimentary" and a "stub for deterministic output," using a fixed-seed xorshift and truncating states beyond 32 basis amplitudes.

## 5. Rendering, Runtime & Browser-Embedding Support (`webizen-render`, `webizen-runtime`, `webizen-lite-wasm`, `webizen-web`, `webizen-component-harvester`)

Supporting crates that provide 3D scene contracts, a GPU simulation kernel, a minimal WASM MCP endpoint, a browser-only portal, and a one-shot component-generation tool.

*   **`webizen-render`** (v0.0.23, ~4,550 lines, 12 `.rs` files + 5 WGSL shaders): a real, actively-consumed `wgpu` 29 N-dimensional semantic renderer — draws a serde `RenderScene` (nodes/edges/faces, PGA-motor transforms) via `wgpu_renderer.rs`'s `WgpuRenderer` (1,850 lines: camera, immediate-mode draw calls, pick/hover hit-testing, CPU-readback PNG/data-URI output for webview hosts, plus a native windowed swapchain path). `volumetric.rs` (native-only) is a thin SDK facade over `qualia-core-db`'s canonical `PortalGpu` for tensor/mesh/`.10d` upload and picking. `scene_contract.rs` defines the live `RenderScene`/`SceneNode`/`SceneEdge`/`SceneFace`/`Tensor10DProjection` DTO used across the workspace as the studio↔GPU hand-off contract; `telemetry.rs` is a 48-byte `#[repr(C)]` ambient-visualization uniform struct; `audio_contract.rs` provides a dual generative/PCM audio DTO. Confirmed consumed (not orphaned) by `webizen-studio` (native GPU viewport), `webizen-desktop` (`native_surface.rs`, `commands/render_pipeline.rs`, telemetry), and `qualia-client-core`'s `wellfair/anatomy_render.rs` (3D anatomy scene construction).
*   **`webizen-runtime`:** a fixed-timestep, GPU-backed simulation kernel. `kernel.rs` defines the `ComputeBackend` trait, `SimulationKernel<B,L>` tick loop, a `RuntimeCommand` reconfiguration channel, and a `LedgerSink` trait for per-epoch journaling; `clock.rs` is an accumulator-based `FixedStepClock`; `diffusion.rs`/`snapshot.rs` hold config/state and a mutex-guarded double-buffered RGBA frame (`SharedFrameBuffer`) with SHA-256 state hashing; `wgpu_backend.rs`'s `WgpuDiffusionBackend` is the one real `ComputeBackend` — a genuine `wgpu` 29 WGSL 4-neighbor diffusion compute shader over a toroidal grid, double-buffered, with CPU readback. It is genuinely consumed, not just scaffolding: `webizen-desktop/src/runtime.rs` drives it end-to-end (see §4).
*   **`webizen-lite-wasm`:** a mature, single-file (748-line `lib.rs`) WASM crate exposing a browser-local MCP JSON-RPC 2.0 endpoint for read-only ontology sites (e.g. ns.webcivics.net). Its `wasm-ontology` Cargo feature profile deliberately excludes the portal/WebGPU renderer, scientific solver bundle, LLM runtime, native daemon, network stack, and filesystem storage — only N3 parsing, bounded Quin queries, SHACL validation, and modal-logic reasoning ship. It negotiates MCP protocol versions 2025-11-25/2025-06-18/2025-03-26 and exposes 11 tools: `ontology_capabilities`, `hash_iri`, `parse_n3`, `query_quins`, `validate_shacl`, `evaluate_deontic`, `evaluate_epistemic`, `route_paraconsistent`, `evaluate_ltl`, `check_subsumption`, `deontic_govern`. Reference release build: 267,993 bytes raw / 94,971 bytes gzip.
*   **`webizen-web`** (Cargo package `qualia-wasm`): the wasm32-only "Semantic Subjectivity Bifurcation Portal." `qualia_portal.rs`'s `QualiaPortal`/`WebEngine` loads `.q42`/JSON scene payloads, holds a 10D tensor buffer plus an 11-slot telemetry vector, and paints a live Canvas2D visualization each frame (ambient particle field, σ-spectral tensor-node projection, wireframe/points/solid/hybrid modes) with tier detection for WebGPU presence. It also has a minimal `mount_qapp` path generating a small DOM from parsed subject/predicate/object triples.
*   **`webizen-component-harvester`:** a single-file (137-line `main.rs`), one-shot build tool — fetches Shoelace's Custom Elements Manifest JSON and code-generates Dioxus `#[component]` wrapper functions into `generated_dioxus_components.rs` (~2,159 lines, checked in), remapping Shoelace's `--sl-color-*` CSS variables onto `--qualia-*` theme variables.

**Known limitations:** `webizen-render`'s `scene.rs` (a `SceneNode`/`SceneEdge`/`SceneFace` draft with a different field layout than the live `scene_contract.rs`) is dead code — not declared as a module anywhere, superseded and orphaned in the source tree. `audio_contract.rs`'s doc comment self-corrects an earlier "zero-heap" claim: `SpectralParams::sigma` is a `Vec<f32>` and does heap-allocate (only the byte-buffer views are truly zero-copy) — carry that correction forward rather than the original framing. Two live (non-decorative) TODOs remain: a bind-group buffer resize in `pipeline/bind_groups.rs` and unwired projector-motor/telemetry uniforms in `wgpu_renderer.rs`. `shaders/screen.wgsl` has an acknowledged placeholder sRGB-conversion approach. `webizen-runtime`'s render pipeline inside `wgpu_backend.rs` (`RENDER_SHADER`, `create_render_pipeline()`, and the surface/vertex/index/depth-texture fields) is built at construction time but never actually used — no `wgpu::Surface` is ever created, every field stays `None` and is marked `#[allow(dead_code)]` with a "planned for future use" comment; it is dead scaffolding, not a working on-screen render path, and the crate ships exactly one production `ComputeBackend` (diffusion). `webizen-web` is a thin stub: `render_stub.rs`'s `SimpleCanvasRenderer` exists on disk but is dead code (never declared as a module in `lib.rs`); no WebGPU rendering exists despite runtime tier detection reaching for it; and the crate is not referenced by `scripts/build_frontend.ps1` while its `demo.html` expects a `wasm-pack --target web` output that no found build script produces — whether it remains in the active build pipeline (versus superseded by `webizen-studio`'s own WASM bundle) needs confirming rather than assumed. `webizen-component-harvester` is a thin stub with no CLI args/tests and a hardcoded source URL/output path; its generated output is not consumed by any other crate — `webizen-studio` maintains its own, separate `components/shoelace.rs`. `webizen-lite-wasm` has no known gaps (no TODO/mock markers found), though this session did not finish confirming `cargo test -p webizen-lite-wasm` runs green, and its correctness is bounded by the underlying `qualia-core-db` modules it wraps (see CLAUDE.md §8 caveats, e.g. the `logic.rs` vs. `temporal_ltl.rs` LTL distinction, which this crate correctly uses the real module for).

## 6. Cooperative Governance & Supported Agency (`qualia-cooperative-core`)

A fully-implemented (~3,850 lines, 84 tests), stub-free domain crate hosting the "supported agency" / cooperative-governance model, consumed by `qualia-client-core` and `webizen-desktop`.

*   **Taxonomy Engine:** `taxonomy.rs` — an open, runtime-extensible `Taxonomy`/`TaxonomyTerm` registry underlying every vocabulary in the crate.
*   **Authority & Domains:** `authority_type.rs` defines a faceted `AuthorityProfile` (modality × trigger × accountability) for "supported agency" relationships with named presets (professional delegation, developmental scaffolding, crisis-activated, parens-patriae fallback); `agency_domain.rs` seeds 17 domains of agency (medical, financial, legal, reproductive/biometric/genetic, etc.) across 4 categories, flagged selfhood-vs-personhood and consequential.
*   **Trigger Algebra:** `trigger.rs` — a recursive `Trigger` type (`VerifiableEvent`, `TemporalWindow`, `DeadmanSwitch`, `HumanConsensus`, `All`/`Any`/`Not`) with a bounded, deterministic `evaluate()`.
*   **Provenance & Delegation:** `provenance.rs` implements a `JudgementProvenance` DAG (`AgentRef`/`Reliance`/dual-timed veracity, `RelianceDeclaration`, and `has_undeclared_ai()` integrity-breach detection); `agency_delegation.rs`'s `delegation_permits()` is a fail-closed ABAC evaluator enforcing selfhood non-delegation and consequential-judgement provenance requirements.
*   **Work Items & Kanban:** `work_item.rs` — event-sourced, replay-safe `WorkItem`/`WorkItemStatusEvent` status derivation and `derive_board()` Kanban projection.
*   **Companion Qapp Packaging:** `qapp_package/manifest.rs` defines `QappManifest` (kind, least-privilege `Capability` scopes, content-addressed `WasmRef`, PWA presentation metadata); `qapp_package/pwa.rs`'s `generate_pwa()` turns a manifest into a `PwaBundle` (manifest.webmanifest, cache-first sw.js, index.html loader).

**Known limitations:** none found in this crate's own source (grep-clean of stub/mock/TODO/`unimplemented!` markers). The `qapp_package` module's own doc comment names two adjacent-but-out-of-scope pieces as deliberate boundaries, not gaps: it does not serve the PWA over a secure origin, and it does not compile the wasm bundle itself (only references it by path + SHA-256 + size). This crate is a pure, well-tested domain model; whether/how `AgencyDelegation`/`Trigger`/provenance are wired into a live storage/WAL layer lives in the consuming crates and was out of scope for this review.

## 7. Knowledge, Content & Interop Tooling (`qualia-semantic-library`, `qualia-solid-bridge`, `qualia-vision`)

Three crates that turn raw documents, remote Solid pods, and camera/image input into structured, provenance-tagged data the rest of the ecosystem can consume.

*   **`qualia-semantic-library`** (binary `qsl`): turns a messy corpus (PDF/HTML/text/markdown) into a library of self-contained `.hmc` "hypermedia container" ZIP files, each holding verbatim source plus deterministically-derived text/HTML/chunks/CML-Turtle with BLAKE3 integrity hashing (`container/mod.rs`, `manifest.rs`). The ingest pipeline (`ingest/mod.rs`, `extract.rs`, `chunk.rs`, `cml.rs`) is deterministic and LLM-free; a separate, explicitly optional HTTP seam (`llm/mod.rs`'s `LlmBackend` trait, implemented today by `llm/ollama.rs`) adds embeddings and topic-tag extraction as an enrichment pass — the crate's own docs are explicit this external LLM is never wired into QualiaDB's core inference. On top of embedded containers, `library.rs` gives manifest-only cataloguing, exact/near-duplicate detection, semantic search, and novelty ranking; `reorganize.rs` proposes/applies a human-browsable copy of the content-addressed store.
*   **`qualia-solid-bridge`:** a working W3C Solid/LDP bridge with two roles — (1) a filesystem-backed personal pod server (`pod_store.rs`) exposing real GET/PUT/POST/DELETE over an LDP container tree (`ldp_translator.rs`, via `warp`), with path-traversal protection, and (2) a consumer/relying-party HTTP client (`consumer.rs`, via `reqwest`) that fetches/PUTs Turtle to remote pods and converts Turtle into `NQuin`s at an "allocation firewall" boundary (`turtle_to_quins`). `solid_proxy.rs` composes routes and runs the Tokio daemon; `vocab.rs` holds canonical LDP/ACL/Solid-terms IRI constants.
*   **`qualia-vision`:** a Phase-1 crate implementing the native visual-intelligence plan. `types.rs` defines a stable, caller-buffered `VisualModel` ABI (`ImageView`, `Detection`, no hidden heap allocation); `cpu_reference.rs`'s `CpuReferenceVision` is the one working implementation — a deterministic 2×2-grid colour/edge-energy classifier; `semantic.rs` compiles detections into 48-byte `VisionQuin` "epistemic observation" records, `q_hash`-tagged and explicitly marked low-assurance/reference-backend rather than ground truth.

**Known limitations (all self-labeled in source, not hidden):** `qualia-semantic-library/src/ontology.rs::fetch_domain_ontology` is explicitly commented **MOCK** — it never fetches/parses/caches a real domain ontology and always returns the same hardcoded generic SHACL shape regardless of `domain_id`. This is not a dead stub: `webizen-desktop/src/commands/mod.rs` exposes it as the live `fetch_domain_ontology` Tauri command, so `webizen-studio`'s `QAppEngine` dynamic-form rendering — across all 274 discipline qapps described in §4 — currently runs on mock ontology data for every domain. EPUB extraction (`ingest/extract.rs`) is not implemented (produces an empty text/HTML asset plus a note; PDF/HTML/text/markdown extraction are real). In `qualia-solid-bridge`, `ldp_translator.rs::compile_wac_to_bytecode` compiles WAC `.acl` bodies into `WebizenOpcode` bytecode and is unit-tested, but it is **never invoked** from the live route handlers — there is currently no access-control enforcement on the personal pod; any request can read/write/delete any resource under the pod root. `consumer.rs::turtle_to_quins` is a deliberately best-effort, line-oriented Turtle parser (not a spec-complete RDF grammar — documented in-line as intentional). `oidc_micro_idp.rs` ships a demo-only mock Solid-OIDC identity provider (placeholder JWKS key, opaque non-JWT tokens, auto-approve authorize, stub register), correctly and openly labeled non-production in both its file header and `NON_GOALS.md`, off by default (`QUALIA_SOLID_DEMO_OIDC=1`). `qualia-vision` is thin-stub status: `CpuReferenceVision` is a heuristic, not a neural detector (doc comments say so directly); the `gpu` feature flag is empty ("Future: wire shared wgpu + forge for detector backends"); no other crate in the workspace currently depends on `qualia-vision`; and `RgbF32` pixel format is unhandled in `sample_rgb`.

## 8. Companion Device Bridge (`qualia-mobile-harness`)

A small Dioxus WASM PWA (2 Rust source files, ~530 lines) acting as a phone-side companion to the WellFair desktop app.

*   **Pairing & Transport:** `main.rs` drives the whole UI/state machine — scans a QR code (or accepts a manual `ws://` URL), opens a WebSocket, authenticates via a signed Ed25519 pairing challenge, then lets the user pick Samsung Health CSV files from the phone's file picker, bundles them (via `wellfare-core`) into a `CompanionHealthBundle`, and pushes the bundle to the desktop over the same WebSocket (or clipboard/OS share-sheet as fallback).
*   **Device Identity:** `companion_device.rs` generates/loads a persistent per-device Ed25519 identity (device id + signing-key seed) from `localStorage`, and signs/verifies the `CompanionChallenge` under `COMPANION_PAIRING_CONTEXT`.
*   **Local Vault Worker (present but unwired — see below):** `assets/sync_io_worker.js` is a complete Web Worker implementing synchronous OPFS block I/O (INIT_VAULT/OPEN_SUPERBLOCK/READ_BYTES/WRITE_BYTES/CLOSE_SUPERBLOCK), intended to back a local WAL-persisted vault.

**Known limitations:** the pairing/WebSocket/CSV-bundle flow itself is real, wired code (no unimplemented!()/TODO/mock markers). But the "local vault" half of the crate is inert: `Cargo.toml` declares `android_pwa_edge`/`ios_pwa_edge`/`opfs_storage`/`wal_persistence`/`crdt_dvv_eae`/`wasm_simd` features and an optional `qualia-core-db` dependency, and `sync_io_worker.js` is a complete OPFS-worker implementation, yet nothing in `src/*.rs` has any `cfg(feature = ...)` gate or reference to that worker script — those features compile to nothing extra, and the worker is never loaded by the app. The "VaultInit" UI state calls the File System Access API's `requestDirectoryAccess()` but only checks the picker succeeded; it never actually opens or uses a superblock via the worker, so the on-device durable-storage/CRDT-sync capability implied by the feature flags is not yet connected to any UI or Rust logic.

## 9. Domain Application: Wellfare Health Vault (`wellfare-core`)

The WellFair personal health/welfare vault domain crate — a records-first data model demonstrating QualiaDB's capability as a secure, semantic data vault for physiological, financial, and welfare data. Actively developed, with 192 `#[test]` functions across 35 of its ~41 source files.

*   **Records Core:** `record.rs` defines `RecordEnvelope` (epistemic status, evidence type, sensitivity class) compiled to QualiaDB's 48-byte `NQuin` quins via FNV-1a `q_hash`.
*   **Data Ingestion & Parsing:** `models.rs` (Weight/Sleep/HeartRate/Steps + clinical `PathologyObservation`/`DiagnosticReport`); `parser.rs` natively parses Samsung Health CSV exports with datetime/offset normalization.
*   **Semantic Translation:** `rdf.rs` serializes parsed records into schema.org/FHIR-flavoured Turtle; `store.rs` is an in-memory oxigraph-backed SPARQL 1.1 store (load Turtle, run SELECT/ASK/CONSTRUCT).
*   **Validation & Rules:** `shapes.rs` applies SHACL-equivalent constraints (as SPARQL ASK queries); `n3_rules.rs` ports the legacy N3Logic clinical rule engine into SPARQL aggregation routed through Webizen lanes; `webizen.rs` is a zero-allocation `WebizenVM` constraint engine enforcing health-policy routing.
*   **Clinical & Credential Model:** `clinical.rs` handles manually-entered clinical documents (pathology, imaging, discharge, referral) with a claim-approval lifecycle; `credentials.rs` caches verifiable-credential status against a local trust list, with JSON-field selective disclosure.
*   **Guardianship & Authority:** `guardianship.rs` implements M-of-N co-signature escrow for proxy/supporter writes; `authority_attestation.rs` generalizes authority attestation (government letters are one preset) with agent-in-capacity and multiple representations.
*   **Finance & Wellbeing:** `finance.rs` is a signed, replay-safe personal ledger with add-wins-by-id merge and pure-derivation balances; `assessment.rs` is a data-driven self-report wellbeing scoring engine shipping PHQ-9 and GAD-7, explicitly non-diagnostic.
*   **3D Anatomy Qapp:** `anatomy/mod.rs` — the Factor/body-system model, per-system burden accumulation, temporal kinetics, dyad/birth/guardianship, investigative pathways, and scorecards.
*   **Companion Sync:** `companion_sync.rs` — the phone-to-desktop wire protocol (Ed25519 pairing, CSV health-bundle transport, live-share usage agreements) consumed by `qualia-mobile-harness` (§8); `companion_pairing.rs` is the underlying Ed25519 challenge-response wire types.
*   **Cooperative Projects & Welfare Support:** `projects.rs` (557 lines) is a real, tested shared-work ledger — distinct from Kanban/task tooling — modeling `Project`, `ProjectMembership` (Steward/Contributor/Observer), and immutable per-contributor `Contribution` records (effort minutes and/or capital cents, with an ROI multiplier and a privacy level). `merge_contributions` (add-wins by id) and `derive_obligations` (pure derivation) mirror `finance.rs`'s "never sum-merge" safety discipline. This is a *separate* concept from `qualia-cooperative-core`'s Kanban/WorkItem model (§6) — the two crates have no compile-time dependency on each other — but they're bridged one layer up: `qualia-client-core`'s `wellfair/api.rs::work_item_board()` derives a Kanban board scoped to a wellfare-core `Project` by matching on a shared `project_id` string convention, not a type-level contract. `welfare_support.rs` (373 lines) is the separate demand/supply model for government benefit assistance: `AssistanceNeed` (category/urgency), `WelfareStream` (program, case reference, status — e.g. "JobSeeker Payment", "Disability Support Pension"), and `GovernmentLetter` (indexable envelope over an out-of-band letter blob). Both are real, tested, and wired through to live Tauri commands in `webizen-desktop`.
*   **Further Records (all real, tested, `RecordEnvelope`-backed, wired into `qualia-client-core::wellfair::api.rs`):** `conditions.rs` (self-reported condition/allergy reports); `life_records.rs` (life events, welfare-case management, case tasks); `personal_records.rs` (disputed-diagnosis reports, housing-safety reports); `medication.rs` (medication catalog/administration, diet entries); `live_share.rs` (companion "live section share" usage-agreement/request/decision protocol); `sleep_analytics.rs` (non-diagnostic sleep-debt and weekly-heatmap computation over real sample data); `mental_wellbeing.rs` (wellbeing observations and therapy notes — explicitly "no licensed instruments," distinct from `assessment.rs`'s PHQ-9/GAD-7); `wasm.rs` (the crate's `#[wasm_bindgen]` browser entry point — CSV→JSON/Turtle parsers, `WasmHealthStore`, N3-rule evaluation, SHACL/quin validation); `qualia_bindings.rs` (a WASM-only in-memory quint store — its own doc comment flags full `qualia-core-db` wiring as deliberately deferred, gated behind a `qualia` feature to avoid pulling `wgpu` into the default WASM binary).

**Known limitations — mostly deliberate, documented boundaries rather than gaps:** `clinical.rs` explicitly does **not** implement PDF parsing for pathology/imaging documents, by design, to avoid a mock extractor masquerading as real extraction. `credentials.rs::VerificationState` documents itself as a local trust-list cache, not real cryptographic signature or revocation verification — real proof verification is deferred to the identity/key-vault layer. `assessment.rs` ships only PHQ-9 and GAD-7; adding further instruments (DASS-21, K10, the Pearson-licensed BDI-II) is deliberately deferred pending Timothy's sign-off, not an oversight. `projects.rs`'s link to `qualia-cooperative-core`'s Kanban model is a string-key convention (`project_id`), not a compile-time contract — nothing stops a `WorkItem.project_id` pointing at a `Project` that doesn't exist; a reader of `projects.rs` alone won't discover the Kanban linkage, which only appears in `qualia-client-core/src/wellfair/api.rs`. `qualia_bindings.rs` is self-declared incomplete (full `qualia-core-db` wiring deferred as "W10"). `qualia_bindings.rs` and `companion_pairing.rs` have no in-crate test coverage (companion_pairing's correctness is exercised, if at all, from the `webizen-desktop` caller side). The crate's own `DIRECTORY_INDEX.md` is stale (dated 2026-06-30, predating `anatomy/`, `guardianship.rs`, `authority_attestation.rs`, `projects.rs`, `welfare_support.rs`, and a dozen other files now documented above) and should not be treated as ground truth.
