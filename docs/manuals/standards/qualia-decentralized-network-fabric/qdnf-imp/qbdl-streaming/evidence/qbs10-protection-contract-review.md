# QBS-10 protection contract review and proposed freeze

2026-11-12. Read-only source review of qbs10-protection-contract-draft.md. No object crypto implementation, build, or qualification was performed. Endpoint sources remain frozen for root compilation. The following narrows the approved implementation direction; final wire bytes and parent file claims still require root freeze.

## Findings that affect the contract

1. Reuse central recipient custody. KeyManager already supports real ML-KEM-768 generation/storage under the historical KeyAlgorithm::Kyber spelling. That spelling is local metadata, not permission to send historical Kyber bytes. Add a typed X25519 algorithm in the same manager rather than treating an EdDSA seed as a recipient DH key or creating a second vault.
2. Explicitly exclude X25519 from generic signing. SignatureEngine::sign_data and verify_signature currently use an Ed25519/hash fallback for otherwise-unmatched algorithms. A new X25519 enum variant must be rejected by these two dispatches; merely adding generator support would otherwise make a DH key usable through that fallback. Preserve behavior for existing algorithm variants.
3. The QBS-05 length-zero ciphertext tree has zero leaves and no valid leaf index. Freeze empty entries as NO entry key, wrap, nonce, ciphertext or AEAD tag. Their emptiness and mapping are authenticated by encrypted metadata and the signed protected descriptor's exact empty tree root. Never manufacture a tag-only leaf at index zero or claim an absent tag was checked.
4. Public protected metadata must exclude all private plaintext commitments, not only paths: original source/header/index hashes, source offsets, semantic closure/policy/consumer hashes and original entry IDs/types stay encrypted. Plain SourceCommit and ContextParameters cannot serve as the public protected descriptor. Public policy/privacy identifiers must be independently opaque random tokens or reviewed salted commitments, not dictionary-testable private content hashes. Public recipient/issuer identity, length and access-pattern leakage is explicit unless separately hidden.
5. Header/index/gap bytes require complete protected coverage. Original padding/gaps can contain arbitrary sensitive bytes; encrypt them as counted opaque objects or refuse unsupported coverage. Do not assume gaps are harmless zero padding. Current whole-source grant semantics remain all-or-nothing.
6. Provider and content-key admission are not application disclosure authority. Managed recipient policy permits decapsulation/derivation; actual recognized publisher/recipient proofs and the same current AuthorityOwner/whole-source policy guard still govern plaintext acceptance. Never replace this composition with a caller-supplied boolean or arbitrary wire key pair.

## Proposed exact profile choices

- Keep the draft acyclic order: random publication attempt/context -> payload encryption and roots -> encrypted metadata -> protected descriptor and recognized publisher signature. AAD/KDF never includes the descriptor/root being produced.
- Freeze logical per-key maximum at 2^20 leaves and 2^34 plaintext bytes (16 GiB), including metadata under its own separately smaller metadata cap. Every individual AEAD input is <=16384 bytes. This is a conservative implementation cap, not a derived universal forgery or post-quantum security bound. The 1 TiB proof geometry does not raise it. Larger original entries fail closed until a reviewed segmentation/key schedule profile exists.
- Exact nonce remains four zero bytes plus u64be leaf index, under a new independently generated entry key for every publication attempt. No object key reuse across entry, role, metadata or attempt. Burn the index before crypto/sink effects and poison on any error/unwind; failed callers never retry encryption with the same index/key. Retry means exact persisted ciphertext replay or an entirely fresh attempt/key/context. No writer-state import or counter-hint restart API.
- Empty entries have length zero, canonical empty ciphertext-representation root, key-present=false, zero wrap count and no leaf request. Their private authenticated metadata row carries the exact empty original mapping. The current-use consumer can return an empty result only after that metadata and publisher authority are accepted.
- Whole-source recipients can receive one hybrid wrap of the metadata key, with per-entry keys only inside encrypted metadata. This avoids an unbounded recipients-times-entries wrap list and matches current all-or-nothing local adoption. Proposed bounds: <=16 recipient wraps and <=4096 total opaque object rows (including gap objects); encrypted metadata <=8 MiB. Each counted object has a distinct key. Entry-subset delegation would require a later explicitly different rights/profile decision. This topology remains a root decision, not silently implemented.
- Recipient key records must bind full recipient identity, both ML-KEM/X25519 public keys (or full SHA384 algorithm-domain key IDs), key epoch, purpose and validity via existing recognized paired COSE PinAuthority proofs. A paired signing receipt alone does not identify KEM keys unless its signed payload includes those exact keys/IDs. Wire records cannot declare themselves trusted recipient roles.
- Proposed hybrid wrap uses existing ML-KEM-768 encapsulation and fresh X25519 ephemeral lease, rejects zero DH, and feeds kem32||dh32 into existing HKDF-SHA384. Freeze a distinct wrap-context digest over suite, publication context, opaque object/metadata identity, generation, epoch, recipient full identity, both public-key IDs, ephemeral X25519 public key and ML-KEM ciphertext. Use that digest as HKDF salt, fixed object-wrap/v1 info, and wrap-context bytes as AEAD AAD. A fresh one-shot KEK permits fixed zero nonce for the single 32-byte content-key wrap. Never expose KEK/shared secrets. Exact byte codec/domain spellings still need independent fixture freeze before code.
- Unwrap verifies its canonical bounded envelope, recognized recipient scope/current policy and stored key IDs before provider work, then repeats fresh current policy/generation/time checks before creating a private decryption-only key handle. Any failed tag ends that handle; reopening is another managed admitted operation and is not a claimed global per-key forgery-attempt budget. Existing runtime admission must cap repeated unwrap attempts. No numerical global verification bound can be claimed without that concrete shared owner.
- Verify recognized publisher signature and exact ciphertext inclusion before AEAD. AEAD writes only private borrowed scratch; decrypt_in_place explicitly leaves failure contents unspecified, so a guard zeros the ENTIRE scratch on error/unwind and after the bounded consumer callback. After successful tag verification, a second fresh same-owner policy/current receipt check must cover plaintext callback acceptance. Do not publish plaintext into an ordinary shared output slice before this check.

Nonce uniqueness follows from the enforced one-writer/one-attempt key scope and burned per-key counters, not from a caller promise. RFC 8439 requires a unique nonce for every invocation under a key and has a per-invocation ChaCha counter limit; these are different from aggregate key-use/forgery limits. See [RFC 8439 §2.8 and §4](https://www.rfc-editor.org/rfc/rfc8439.html#section-2.8). HKDF domain binding reuses [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869.html). The proposed hybrid/application construction remains unqualified pending independent review/vectors.

## Exact parent impact and next source claims

Live KeyAlgorithm search across crates found algorithm-model consumers in this central library (plus unrelated platform SecKeyAlgorithm naming). Relevant dispatches use fallback arms; compile exhaustiveness alone cannot establish correct new-variant behavior.

- key_management/types.rs: append explicit X25519 variant, preserve existing serialized names/order/discriminants. key_management/generator.rs: registration + X25519 generation/public derivation dispatch only; move implementation into a focused child because generator currently exceeds500 lines. Existing Kyber generator remains unchanged.
- key_management/manager.rs: optionally route X25519 to existing keyexchange zone; preserve legacy selection for all other variants. Existing borrowed lookup suffices, no cloned getter needed.
- signing.rs: two narrow explicit X25519 unsupported branches in sign_data and verify_signature; no change to existing algorithm defaults. Without these branches the new key would enter the legacy Ed25519 fallback.
- key_management/access/managed_policy.rs: operation-parameterized strict helper plus compatibility Sign wrapper. Keep trusted authenticated context; aliases may improve neutral naming without introducing authentication infrastructure.
- key_management/managed_signing.rs and a NEW managed_control.rs: move existing mutex fence without behavioral change, preserve public SigningControl API. Alternatively expose a bounded internal control method there; no duplicate control state.
- crypto/network/types.rs: reviewed appended object recipient/content purposes with distinct values; audit all purpose matches. Existing purposes/wire profiles unchanged.
- NEW library/managed_object.rs facade and key_management/managed_object/{recipient,seal,open,tests}.rs own capabilities through existing manager. NEW crypto/network/object_stream/{types,context,aad,wrap,tests}.rs own bounded wire adapters only. NEW bundle/stream/protection/ owns authenticated descriptor/proof/current-use composition. Root owns all parent routing, profile/registry freeze and Cargo.
- Existing generic KeyRotator synthesizes sized random bytes; it does not preserve a valid ML-KEM pair. Managed paired recipient rotation must call the real existing generator for both successor keys and advance the actual control/recognized recipient binding. Do not route through generic rotate_key or change unrelated legacy rotation in this increment.

Required focused tests include borrowed custody/no exported private Key, both mandatory policies and all strict negatives, exact algorithm/key-ID mismatch, valid ML-KEM public reconstruction, X25519 signing refusal, cancel/rotation/deadline during decapsulation, wrong recipient/proof/wrap, empty/no-key row refusal when malformed, nonce burn on sink failure/unwind, whole scratch erasure and zero consumer calls before current authentication. Independent AEAD/HKDF/wrap-context vectors must exercise actual production helpers. Full core ownership tests remain root-run.
