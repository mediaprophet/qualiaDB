# QBS-10 protected-object composition — review draft

2026-11-12. Design preparation, not implemented or qualified. QBS-03/04/05/06 acceptance remains a dependency. This document narrows the next crypto review; it does not authorize a public confidentiality claim.

## Existing owners

Inspected crypto/DIRECTORY_INDEX.md and actual crypto/network/{aead,kdf,secret_lease,types}.rs, crypto/sanctuary_crypto.rs, and specialized_libs/cryptographic_library/{library,key_management/managed_signing}.rs. Existing central CryptographicLibrary owns KeyManager, access policies, providers and encryption operations. Network aead already supplies caller-buffered ChaCha20-Poly1305 with a 32-byte key, 12-byte nonce and 16-byte detached tag. Network kdf supplies HKDF-SHA384. Sanctuary supplies AES-GCM/ChaCha/XChaCha and storage-specific nonce derivation; its PIN/volume framing must not be relabeled as this network protocol. Existing central convenience encryption returns owned buffers and selects random nonces; add a bounded managed-operation child there for streaming rather than create another vault or use cloned long-term key bytes.

Production signing remains existing managed paired COSE. Session authentication remains QSession with independent received Finished checks. TLS/DTLS/WSS carriage alone supplies no post-quantum assurance. Symmetric object confidentiality additionally needs a PQ recipient key-establishment path, managed recipient access and exact current scope.

## Proposed acyclic construction

A protected outer profile must be distinct from QASD plain v1. Do not reuse the plain publisher's original header/index/source SHA384 fields in publicly visible ciphertext metadata: they expose private content identities and inventory. First generate an OS-random publication nonce and exact public protection context containing protocol/suite/version, opaque publication identity, generation, policy/privacy scope and key epoch. Canonicalize and commit this context BEFORE encrypting. It contains no resulting ciphertext root and no final descriptor ID.

Each encrypted object has an opaque entry identifier, exact logical length and a unique managed 256-bit content key generated for this publication attempt. Entry-specific key scope commits the full context ID, entry identifier, generation, epoch and purpose. Header/index/original path/type/content hashes and mappings belong in an encrypted metadata object with its own key/scope. Public lengths/access patterns remain observable unless a separate reviewed padding profile is defined. There is no implicit claim that encrypting payload hides its inventory.

Use the existing 16 KiB logical proof leaves. Proposed nonce is exactly 12 bytes: four zero bytes followed by the leaf index as u64 big endian, under a distinct key for this entry and attempt. AAD has an explicit versioned domain and fixed-width context ID48, entry ID4, generation8, epoch4, total plaintext length8, leaf index8 and this leaf plaintext length4, all integer fields big endian. Ciphertext leaf bytes are ciphertext followed by tag16. QBS-05 ciphertext representation hashes these exact encoded bytes with its existing distinct representation/epoch framing. Encrypt first, build ciphertext roots second, build/sign the final protected descriptor last. No final root or descriptor ID enters its own encryption AAD/KDF.

The proof library's 1 TiB geometry ceiling is not automatically an encryption usage allowance. Propose a smaller explicit per-key limit for review, with checked maximum leaf count, cumulative bytes and verification attempts. Empty entries need an authenticated empty-object representation decision; do not silently treat an absent AEAD tag as encrypted empty plaintext. Metadata and payload keys/nonces must never share a domain or a key.

## Nonce ownership, retries and plaintext lifetime

A producer capability must be non-Copy/non-Clone, owned by the existing managed provider, and consume each leaf index before any encryption or sink callback. Reject duplicate/decreasing indices and fail terminally after a partial effect or unwind. Sealing keys cannot be imported from arbitrary raw arrays through production APIs. On crash/restart, do not reconstruct a writer from a counter hint: begin a new key/publication attempt, or replay previously persisted exact ciphertext bytes. Restartable encryption under the same key needs a separately reviewed durable counter reservation owner; it is not provided by the current unkeyed bitmap/checkpoint.

Recipient capabilities decrypt only. An unwrap must not create a sealing capability for the same key. Receiver verification first checks recognized descriptor/ciphertext inclusion and all scope fields. AEAD decrypts into a private borrowed scratch guard that erases on failure, cancellation and unwind. No plaintext consumer callback or output handle exists before successful tag verification plus fresh current authority/policy checks. A successful callback remains bounded and synchronous until a real consumer lease/drain owner is connected. No raw key or reusable boolean authorizes later reads.

Recipient wraps bind full recipient identity, context, entry/key scope, generation, epoch, algorithm suite and both hybrid public-key references. Existing ML-KEM-768/X25519 primitives must remain owned by central managed recipient custody; exact wrap envelope, KDF inputs/labels and ephemeral-key lifetime require review. Sender possession and valid encapsulation are not recipient authorization. Removing a published wrap cannot revoke a content key already learned; rotation protects newly encrypted generations only. Cache privacy classes prevent public/private plaintext aliasing.

## Integration and acceptance work

Exact proposed children: crypto/network/object_stream/ for strict fixed-byte context/AAD/leaf codec, specialized_libs/cryptographic_library/key_management/managed_object/ for existing-manager operation custody, bundle/stream/protection/ for authenticated descriptor/proof/recipient/consumer composition. Root retains parent routing and Cargo. No new crypto primitive, parallel registry or raw-secret public API.

Before implementation freeze: resolve managed KEM recipient ownership already present in the tree; select explicit usage limits and empty representation; freeze canonical protected descriptor and wrap bytes; prove full domain/nonce uniqueness; review caller buffer accounting and cancellation boundaries. Then independent Node/OpenSSL AEAD/HKDF fixtures plus actual managed-provider tests must cover tag/AAD/context/epoch/index tampering, duplicate/retry/crash attempts, key rotation, cancelled/late unwrap, private scratch erasure, wrong recipient, malformed wraps, confidential metadata and absence of plaintext before authentication. Test production owner composition, not fake Allow/confirmed providers.

Reference rationale: [RFC 8439 section 2.8](https://www.rfc-editor.org/rfc/rfc8439.html#section-2.8) defines the existing AEAD framing and nonce requirements; [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869.html) defines the reused extract/expand primitive. These references do not qualify the proposed Qualia composition. Exact profile review and external qualification remain required.
