Design direction · Human-Centric Authoring

Author a shared tool
without losing the people, reasons, or limits behind it.

A Semantic Instrument authoring environment should feel less like programming an institution and more like carefully making an agreement, method, or professional practice clear. It starts with a human purpose; it then helps people make vocabulary, evidence, authority, privacy, boundaries, and review explicit.

This is a product and interaction-design direction, not a claim that every screen described below is already shipped. It describes the capability Webizen and QualiaDB should make possible—and the safeguards an implementation must preserve.

Authoring path

From “what are we trying to do?” to a bounded, reviewable instrument

1. Purpose

Name the practical question, affected people, intended benefit, and what must not be decided.

2. Participants

Capture positions, roles, mandates, consent conditions, dissent, and review rights.

3. Meaning & evidence

Link shared terms to sources, claims, assumptions, dates, confidence, and provenance.

4. Boundaries

Set permitted uses, disclosure paths, holds, escalation, privacy, and ZK predicates.

5. Rehearse

Run plain-language examples and edge cases before anyone relies on the rule.

6. Govern release

Ratify, version, publish or keep private, then retain run and review receipts.

The workspace people need

Several views of one accountable instrument—not a maze of technical tabs

Plain-language brief

Purpose, affected people, benefit, risks, excluded outcomes, and the question that the tool is actually allowed to answer. The machine form must remain traceable to this readable brief.

Agreement and authority

A place for people to contribute, qualify, dissent, authorise, delegate narrowly, challenge, or withdraw. An incorporated entity and an AI agent never erase accountable human involvement.

Meaning map

A visual, inspectable connection between terms, ontologies, claims, sources, and rules. Advanced authors can work directly with RDF, SHACL, logic, or code; other contributors should not have to start there.

Evidence timeline

Show what was known when, what changed later, which assumptions expired, and which material changes trigger reconsideration or remedy. History is linked, not silently overwritten.

Disclosure composer

Specify what a routine verifier can learn, what remains protected, who may seek controlled disclosure, for what purpose, under which procedure, and with what receipt. A proof is not mistaken for an access-control system.

Rehearsal and review

Test examples, counter-examples, missing data, conflict, temporal change, and escalation before activation. Show why a result is ready, held, or requires human review.

Relation to ontology editors

Not “better than Protégé” at everything—broader around the human work that makes a rule legitimate

Protégé is an established specialist environment for ontology engineering and reasoning. A human-centric authoring environment should retain that level of semantic precision and interoperability, while adding the surrounding work needed to make a semantic model usable as an accountable instrument. The point is complementarity, not an unsupported replacement claim.

Interaction principles

What makes it human-centric in use

  • Meaning before syntax: people may begin in ordinary language, diagrams, examples, and references; formal representations remain inspectable rather than hidden.
  • No forced certainty: a claim, assumption, source, dissent, or unresolved question stays distinguishable from an accepted term.
  • Progressive precision: begin with a small, safe tool; add terms, constraints, logic, proofs, and automation only when the purpose requires them.
  • Fail visibly: missing authority, evidence, privacy conditions, or inputs produces a clear hold or escalation—not a fabricated answer.
  • Every automation is challengeable: people can inspect the basis, identify accountable roles, request review, and produce a revised instrument without erasing prior context.

Non-negotiable boundary

The environment helps people articulate and run rules. It does not acquire authority for them.

An attractive visual editor can make an unexamined rule look finished. The product must therefore keep scope, consequences, accountable human authority, consent or applicable procedure, uncertainty, and review in view at the same time as it makes semantic modelling easier.

No company, incorporated entity, or AI agent is the final accountable author merely because it stored, generated, or executed a model.

Delivery architecture · target state

One POET authoring workspace, launched by the newer Desktop system and grounded in QualiaDB

This must not be framed as an enhancement of the earlier Webizen Desktop UI. That UI is a failed product surface and remains only as a migration path while the newer OS-like Desktop shell is developed. The intended authoring experience is a first-class POET application launched by that newer shell, using QualiaDB for local semantic storage, reasoning, validation, provenance, and bounded execution.

NEW DESKTOP SYSTEM

The trustworthy local host

Launches POET as an application, exposes local files, browser, renderer, model runtime, permissions, and settings as visible capabilities—not hidden configuration or an agent-only service. It owns the local safety boundary, rather than pretending a canvas alone can do so.

POET

The comprehensible authoring place

Provides the relational canvas: a mind-map-like visual workspace where concepts, sources, claims, rules, people’s positions, constraints, and consequences are connected. Each connector has inspectable semantics and logic; it is not merely a line drawn between cards.

QUALIADB / WEBIZEN ENGINE

The bounded semantic substrate

Holds and evaluates the structured model: ontology mappings, constraints, modalities, agreement state, proofs, provenance, temporal conditions, and receipts. It returns structured explanations and holds; it does not substitute a machine’s authority for human authority.

How a selected generative agent participates

An author may select a local or otherwise permitted generative agent to help explore a model: suggest terms, find potential relations, draft plain-language alternatives, propose mappings between chosen ontologies, generate test cases, or explain a constraint. The agent works in a bounded drafting lane, not an invisible control plane.

Visible inputs

The author chooses which ontologies, records, references, and tool permissions the agent may use.

Inspectable proposals

Every proposed node, connector, rule, or mapping is shown as a change that people can accept, amend, reject, or hold.

Human ratification

Only accountable people can adopt an agreement, activate an instrument, authorise disclosure, or permit an operational agent to act.

The current work contains relevant foundations—ontology import and layout, graph/canvas rendering, local model and agent configuration paths, semantic-instrument lifecycle controls, and reasoning modules. Joining them into this single POET authoring journey is the product integration work still required; it should not be represented as complete before the end-to-end workflow is real.

WASM POET · collaboration and demonstration

A browser can be a shared authoring place—without becoming an unbounded authority or a misleading demo

POET’s WASM form is valuable not merely as a fallback viewer. It can make a selected semantic workspace available to collaborators without requiring every participant to install a desktop application first. In this model, a manifold is a shared, bounded working space: a visible arrangement of concepts, relations, evidence, rules, questions, and proposed changes, with the semantic structure behind each connector.

Collaborative manifold

Participants see the same selected graph and can propose nodes, relations, comments, alternatives, and tests. Each change is attributable, versioned, and reviewable; competing interpretations can coexist until people resolve or explicitly retain them.

Structured connectors

A connector can mean “is defined by”, “supports”, “contradicts”, “is permitted by”, “depends on”, “was known at”, or another declared relation. POET presents a comprehensible graph while QualiaDB validates the corresponding semantic and logical structure.

Selected agent, bounded role

The workspace can give a selected generative agent access only to declared ontology packs, sources, tools, and permissions. Its output arrives as attributable proposals in the manifold; it cannot merge its own work, broaden disclosure, or activate an instrument.

An honest online POET demo mode

  1. 1. Start with a labelled example manifold. Use sample ontologies, example records, and a clearly stated learning purpose—not a hidden production workspace.
  2. 2. Let people make and inspect changes. They can add concepts, choose relation types, compare ontology mappings, ask the demo agent for a proposal, and see the resulting structured change.
  3. 3. Make limits visible. The demo states whether its state is local to the browser, temporary, or saved; which reasoning is available; and that it cannot authorise decisions, access protected evidence, or make a production release.
  4. 4. Offer a deliberate hand-off. A person can export an inspectable draft or open it in their local Desktop/POET environment for controlled evidence, fuller reasoning, signing, or activation.

Browser boundary

A collaborative browser workspace must not imply that every participant can read every record, use every agent, or access local host capabilities. Membership, purpose, ontology packs, tool permissions, disclosure policy, and version must be declared by the manifold.

Protected data, custodial keys, controlled court disclosure, and authority-bearing actions remain in the appropriately authorised environment. The browser can show a proof, a receipt, or a bounded representation without receiving the underlying protected material.

A practical sequence is: make the demo manifold local-first and inspectable; add explicit collaboration and change review; then add synchronisation only with declared membership, conflict handling, and receipts. “Shared canvas” alone is not sufficient collaboration for a human-centric system.
